# 4. Как это работает

Этот раздел объясняет устройство системы простыми словами: как документы
превращаются в базу знаний, как ищутся ответы и как программа их проверяет.

## 4.1. Индексация: из файла — в базу

```
Файл (DOCX, PDF, …)
   │  parsers/      — разбор формата в список абзацев
   ▼
Абзацы с метками: «пункт 28.1.3», «Глава 6», «заголовок», «таблица», «текст»
   │  structure.py  — дерево документа
   ▼
Глава 6 → 28. Основания отклонения заявки → 28.1 → 28.1.1 … 28.1.7
   │  structure.py  — фрагменты (chunks)
   ▼
Один логический пункт = один фрагмент (длинные режутся по абзацам)
   │  indexer.py    — векторы через qwen3-embedding (1024 числа на фрагмент)
   ▼
PostgreSQL: documents → document_sections (дерево) → document_chunks (текст + вектор)
```

### Почему нельзя просто резать текст каждые N символов

В нормативных документах смысл держится на структуре:

```text
28.1 ЗО отклоняет заявку участника закупки на следующих основаниях:
28.1.1 непредставление документов…
28.1.2 несоответствие участника…
```

Если механически разрезать текст, подпункт `28.1.2` потеряет связь с
«основаниями отклонения». Поэтому каждый пункт хранится отдельно и знает
своего родителя.

### Номера пунктов в DOCX

В документах из КонсультантПлюс номера («28.1.3.», «Глава 6») не записаны в
тексте — их рисует Word по правилам автонумерации. Парсер повторяет логику Word:
общие счётчики для списков одного шаблона, сброс вложенных уровней, формат
номера (`%1.%2.`, `Глава %1`). Элементы вида `1)`, `а)`, `•` считаются частью
пункта, а не отдельными пунктами.

> В первой версии главы («Глава 1») и разделы («1. Сокращения») получали
> одинаковый номер `1`. Теперь главы хранятся как «Глава 1», и коллизий нет.

### Что попадает в вектор

Не только текст пункта, но и его «адрес» — так поиск лучше понимает короткие
подпункты:

```text
Документ: Положение о закупках товаров, работ, услуг
Раздел: Глава 6. ОБЩИЙ ПОРЯДОК… → 28. Основания отклонения заявки → 28.1 → 28.1.3
Пункт: 28.1.3

несоответствие предлагаемой продукции и условий исполнения договора…
```

## 4.2. Поиск: пять каналов

Одного «поиска по смыслу» недостаточно. Например, пользователь спрашивает про
«дополнительный запрос», а в документе написано «дозапрос». Или спрашивает
точно «что в пункте 28.2?». Поэтому работают пять каналов одновременно:

| Канал | Что ищет | Пример |
|---|---|---|
| **vector** | похожие по смыслу фрагменты | «сколько времени на ответ» ↔ «не может превышать 5 рабочих дней» |
| **fts** | слова с учётом русской морфологии | «отклонить» ↔ «отклоняет» |
| **title** | совпадение с названием раздела | «…заявку могут отклонить?» ↔ «28. Основания отклонения заявки» |
| **term** | точные обозначения | «44-ФЗ», «223-ФЗ» |
| **exact** | номер пункта из вопроса | «пункт 28.2», «п. 27.4», «глава 6» |

Результаты объединяются (схема RRF: чем выше место в каждом канале — тем больше
баллов). Совпадение с названием раздела весит вдвое больше, точный номер
пункта — почти гарантирует первое место.

Совпадение с названием раздела считается **сильным**, только если совпало
≥ 2 слов вопроса или название короткое и совпало целиком («27. Дозапрос»).
Случайное совпадение одного слова («запрос» ↔ «Запрос цен») — слабый сигнал.

## 4.3. Контекст для модели

Из 5 лучших результатов собирается контекст:

1. **Раскрытие структуры.** Если раздел найден по названию или номеру, в
   контекст добавляются его подпункты (2 уровня). Нашли «28» → добавляются
   28.1–28.4 и 28.1.1–28.1.7. Нашли «28.1» → раскрывается родитель «28»,
   чтобы попали и соседние 28.2–28.4.
2. **Родительский пункт.** К найденному подпункту добавляется его родитель —
   чтобы модель видела «…на следующих основаниях:».

Каждый фрагмент получает метку `[S1]`, `[S2]`, … Номера пунктов разных
документов не путаются: всё привязано к конкретному документу.

## 4.4. Ответ модели и его проверка

Модель (`qwen3:14b`, без режима «размышлений», температура 0) обязана вернуть
JSON строго по схеме:

```json
{
  "answer_found": true,
  "intro": "Заявку участника могут отклонить по следующим основаниям:",
  "claims": [
    {"text": "Непредставление необходимых документов и сведений", "source": "S4"},
    {"text": "Несоответствие участника требованиям", "source": "S5"}
  ],
  "note": ""
}
```

Дальше работает **программа, а не модель**:

1. **Проверка ссылок.** Утверждение со ссылкой на несуществующую метку
   отбрасывается. Название документа, номер пункта и текст источника берутся
   из базы по метке.
2. **Контроль полноты перечней.** Если вопрос про перечень («какие основания…»,
   «по каким причинам…», «в каких случаях…»), а ответ ссылается на пункт-список
   (заканчивается двоеточием) или его подпункты — программа проверяет, что
   упомянуты **все** подпункты. Пропущенные добавляются (модель кратко их
   формулирует отдельным запросом) и помечаются «добавлено проверкой полноты».

> Это решение проблемы, найденной при первом развёртывании: модель стабильно
> пропускала пункт 28.1.6. Теперь пропуск обнаруживается и исправляется автоматически.

3. **Журнал.** Вопрос, ответ, источники и время сохраняются в `rag_queries`.

## 4.5. Связка с Open WebUI

Open WebUI — готовый чат-интерфейс (учётные записи, история, Markdown).
Свой поиск по документам у него простой: текст режется на куски
фиксированной длины, и структура «глава → пункт» теряется. Поэтому
встроенный поиск Open WebUI для нормативных документов **не используется** —
Open WebUI лишь показывает ответы нашего движка.

```
Open WebUI ──POST /v1/chat/completions──► School AI API (127.0.0.1:8000)
           (model: school-docs,              │
            ключ API_KEY,                    ├─ служебный запрос («### Task:» —
            имя пользователя)                │  название чата, теги)? → сразу в Ollama
                                             ├─ есть история диалога? → модель
                                             │  переписывает вопрос в самостоятельный
                                             │  («а ещё?» → «Какие ещё основания…»)
                                             └─ rag.ask() → ответ в Markdown:
                                                пункты со ссылками + свёрнутый блок
                                                «Тексты источников»
```

Для Open WebUI наш API выглядит как сервис OpenAI с двумя «моделями»:

| Модель | Где ищет |
|---|---|
| `school-docs` — 📘 Документы школы | коллекция `documents` |
| `school-reports` — 📝 Примеры отчётов | коллекция `reports` |

Рядом в списке видна и сама `qwen3:14b` из Ollama — обычный чат без
документов (написать письмо, перевести текст). Ответы по документам — только
через `school-docs`.

Файлы, прикреплённые прямо в чат (скрепка), обрабатывает встроенный поиск
Open WebUI — тоже локально, через ту же embedding-модель. Это удобно для
разового вопроса по одному файлу, но без проверки ссылок и полноты.

## 4.6. Типичное время ответа

| Этап | Время |
|---|---|
| вектор вопроса | ~0,1 с |
| поиск в PostgreSQL | ~0,05 с |
| генерация ответа | 2–15 с (зависит от длины перечня) |
| дополнительный запрос при контроле полноты | +5–10 с |

Основное время — генерация. Посмотреть разбивку: `school-ai ask --debug "…"`
или внизу ответа в веб-интерфейсе.

## 4.7. Что можно улучшить дальше

* **OCR** для сканированных PDF (например, встроенный в macOS Vision).
* **Reranker** — дополнительная модель, переупорядочивающая результаты поиска;
  станет полезен, когда документов будет много.
* **Синонимы / переформулировка вопроса** локальной моделью перед поиском.
* **Файловый менеджер** (FileBrowser) с автоматической индексацией —
  загрузка документов через браузер (сейчас — через `deploy/push-data.sh`).
* **Progress Reports**: отдельная коллекция `reports` уже предусмотрена;
  генерация по данным SkolStream — следующий этап.
